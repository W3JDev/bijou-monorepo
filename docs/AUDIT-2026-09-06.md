# Bijou monorepo — hardening audit, 2026-09-05/06

Branch: `audit/hardening-pass`. Nothing was deployed, nothing was pushed, no
production system was touched, `.env` was not modified.

## How to read this

Every finding is labelled with how it was established:

- **CONFIRMED** — I ran a command myself and the output is quoted here.
- **CONFIRMED (code)** — established by reading the exact lines, quoted here,
  with the reachability of the code path also checked. Not exercised at runtime,
  and the reason for not exercising it is stated.
- **REPORTED** — surfaced by an audit agent, plausible, but I did not personally
  reproduce it. Treat as a lead, not a fact.

That distinction is doing real work here. See § The skeptic panel for why.

## P0-1 Live Coolify API token committed and pushed — CONFIRMED

`ops/coolify/load-agentops-image.sh`, `ops/coolify/PRODUCTION-CUTOVER-PLAN.md`,

A Coolify API token is platform-level control: it reads **every service's
environment variables** — so `SUPABASE_SERVICE_KEY` (unrestricted on all tenant
data, since RLS is service-role-only), `GEMINI_API_KEY`, `STRIPE_SECRET_KEY`,
`ADMIN_API_KEY` — and it can deploy arbitrary images.

This is the **second** credential committed to this repo, and it landed five
days *after* the post-mortem for the first one
(`docs/SECURITY_ALERT_2026-08-24_admin_key.md`). That post-mortem queued a
gitleaks hook and CI secret scan; neither was done. The existing pre-commit
guard did not fire because it does not match the Sanctum `1|…` format.

Fixed in `c29021e` (removed from the working tree, replaced with
`${COOLIFY_API_TOKEN:?}`). **Rotation and history scrubbing are owner actions
and are the only steps that actually help** — any clone taken since 2026-08-29
still has it. Runbook: `docs/SECURITY_ALERT_2026-09-06_coolify_token.md`.

## P0-2 Every successful login overwrites the shared service-role credential — CONFIRMED

`packages/backend/src/saas/auth_api.py:554` (pre-fix line)

`get_supabase()` returns a **process-wide singleton** built with the
service-role key, shared by every `.table()` call in the backend. `auth_api`
ran user-scoped auth on that same object. supabase-py rewrites
`options.headers["Authorization"]` on `SIGNED_IN`, so:

```
login   before: Bearer SERVICE-ROLE-KEY-AAA
login   after : Bearer eyJhbGciOiAiSFMyNTYiL...   <- the user's JWT
BEFORE postgrest Authorization: Bearer SERVICE-ROLE-KEY-AAA
AFTER  postgrest Authorization: Bearer eyJhbGciOiAiSFMyNTYiL...
```

Nothing restores it. Every later request that worker handled — other tenants'
dashboards, the WhatsApp webhook, the schedulers — then authorized as that one
user. Under service-role-only RLS that means empty reads, and a tenant-isolation
break on anything that did land.

Fixed in `89b67f3` with a dedicated auth client. See § The skeptic panel — this
finding is here in a form the original reporter got wrong.

## P0-4 `/webhook/message` and `/webhook/connection` are unauthenticated — CONFIRMED (code)

`packages/backend/src/core/bijou.py:7411` and `:7791`

Neither handler contains any authentication:

```bash
$ sed -n '7411,7491p' src/core/bijou.py | grep -E "Authorization|API_KEY|verify|Depends"
  (no matches)
$ sed -n '7791,7851p' src/core/bijou.py | grep -E "Authorization|API_KEY|verify|Depends"
  (no matches)
```

`/webhook/connection` then takes the tenant from the body —
`tenant_id = data.get("tenant_id")` — and updates that tenant's `whatsapp_jid`.
So an unauthenticated caller can repoint a victim tenant's WhatsApp binding.
`/webhook/message` lets anyone inject fake inbound messages, drive a tenant's
AI and burn its LLM budget.

**Not exercised**, deliberately: both mutate production data.

**Fixed in `2d4b732`** — shared secret, constant-time compare, sent by the
bridge, required in both new compose files. Measured after the fix:

```
no credential      /webhook/message 401   /webhook/connection 401
wrong credential   /webhook/message 401   /webhook/connection 401
correct credential /webhook/message 422   /webhook/connection 503
```

One caveat stated plainly: the check is **fail-open when
`BIJOU_WEBHOOK_SECRET` is unset**, logging CRITICAL. That is a migration path
so upgrading an existing deployment does not drop inbound WhatsApp before an
operator can set the variable — new deploys cannot come up without it. Existing
production is therefore **still open until someone sets that variable**.

Note this interacts with P0-5 — the bridge that is *supposed* to be the only
caller does not reach these endpoints at all as currently configured.

## P0-8 SECURITY DEFINER functions tunnel straight through RLS — CONFIRMED

Found by running Supabase's own advisors once database access was granted, then
confirmed end to end against production.

RLS holds for tables. As `anon`:

```
GET /rest/v1/tenants?select=id        -> 200  []
GET /rest/v1/conversations?...        -> 200  []
```

But 14 SECURITY DEFINER functions in `public` were EXECUTE-able by `anon` and
`authenticated`. A SECURITY DEFINER function runs as its owner and therefore
bypasses RLS, and PostgREST exposes every non-trigger function in an exposed
schema at `/rest/v1/rpc/<name>`. So they were a tunnel through RLS reachable
with the PUBLIC anon key that ships in every browser:

```
POST /rest/v1/rpc/get_tenant_daily_sent_count
     {"p_tenant_id":"<another tenant's uuid>"}   -> 200, returned a value
```

This happens silently: Postgres grants EXECUTE to PUBLIC on every new function
by default, and anon/authenticated inherit from PUBLIC. Nobody wrote a GRANT.

Worst of them:

| Function | Why it matters |
|---|---|
| `search_knowledge(...)` | returns `TABLE(id, title, **content**, ...)` — cross-tenant knowledge-base exfiltration |
| `get_contact_last_campaign(uuid)` | another tenant's campaign history |
| `calculate_campaign_stats(uuid)` | another tenant's campaign metrics |
| `count_monthly_conversations(...)` | another tenant's volume |
| `increment_contact_message(...)` | **writes** to another tenant's counters |
| `cleanup_expired_onboarding_sessions()` | **deletes** rows |
| `cleanup_expired_qr_sessions()` | **deletes** rows |
| `rls_auto_enable()` | event-trigger function, `search_path=pg_catalog` |

Fix written and committed as
`packages/backend/migrations-py/add_revoke_anon_security_definer.sql`. **Not
applied** — writing DDL to production is blocked by a permission guard on my
side. Safe to apply: nothing calls these with the anon key (every `.rpc()` in
the codebase uses the service-role client), and it is reversible with a GRANT.

## P2-7 A `service_role` key is in the local git object store — CONFIRMED

`refs/stash` → `b9000833` ("untracked files on main"), holding
`ops/coolify/.envs-backup.json`.

Scanning every JWT in every reachable object found exactly two distinct tokens:

```
distinct JWTs across ALL history: 2
     1  role='anon'
     1  role='service_role'
files holding any NON-anon JWT:
  role=service_role: ops/coolify/.envs-backup.json
```

The service-role key bypasses RLS entirely — unrestricted read/write on all
tenant data. But the exposure is **local only**, and I want to be precise
because the severity turns on it:

```bash
$ git log --all -- ops/coolify/.envs-backup.json     # -> nothing; never committed to a branch
$ git for-each-ref --contains b9000833
  refs/stash                                          # -> reachable ONLY from the stash
$ git check-ignore -v ops/coolify/.envs-backup.json
  .gitignore:179                                      # -> correctly ignored
```

So it was never pushed and the file is gitignored. It reached the object store
because someone ran `git stash -u`, which sweeps untracked files in. It stays
there until the stash is dropped, and `git push --all` or handing over the repo
directory would expose it.

Fix: `git stash drop` that entry and `git reflog expire --expire-unreachable=now
--all && git gc --prune=now`. Rotation is already required for other reasons
(P0-1), which covers this key too.

# P2 — fragile, will break soon

- **P2-1 CONFIRMED — 3+ GB of unused ML deps in the backend image.**
  `Dockerfile.backend` installs `requirements.txt`, which pins `torch`,
  `torchaudio`, `chatterbox-tts`. Nothing under `src/` imports any of them
  (`grep -rn "import torch\|chatterbox" packages/backend/src/` → no matches).
  The Dockerfile's own comment claims the image stays "under 200 MB". Measured
  with them stripped: **1.36 GB**. The torch-inclusive image was not built, so
  the exact delta is unmeasured.
- **P2-2 CONFIRMED — compose referenced a Dockerfile that does not exist.**
  `dockerfile: Dockerfile.voice` with `context: .`; the file is at
  `packages/voice/Dockerfile.voice`. `--profile voice` could never build. Fixed.
- **P2-3 CONFIRMED — no root `.dockerignore`.** Every root Dockerfile builds
  with `context: .`, so `.git`, `.git.broken`, `.git.broken2`, `node_modules`,
  a Windows `.venv` and the live-secret `.env` were all shipped to the daemon.
  The `COPY` statements are selective, so **no secret reached an image layer** —
  the cost was build time and handing credentials to the daemon. Fixed.
- **P2-4 CONFIRMED — root `Dockerfile` has invalid syntax.**
  `Dockerfile:36`: `COPY packages/backend/scripts /app/scripts 2>/dev/null || true`.
  Shell redirection is not COPY syntax. `Dockerfile.backend` documents this as a
  known bug and fixes it there; the root file still carries it. **Not fixed** —
  see § Deliberately not fixed.
- **P2-5 SUPERSEDED — live RLS state is now known.** All 154 tables have RLS
  enabled; 134 policies exist. CLAUDE.md's claim that `_fix_rls_v6.js` left
  "only service_role" reading and writing is **wrong**: 39 policies target
  `authenticated`. Five of those are unrestricted (`USING (true)`), but they sit
  on `checklist_state`, `sheet_data`, `team_activity` and `user_profiles` —
  tables belonging to the other application sharing this schema, not Bijou's.
  **Bijou's `tenants` / `conversations` / `messages` are properly protected**,
  verified as anon above. The original file-level finding follows.
- **P2-5(orig) CONFIRMED — migrations do not enable RLS on the tables they create.**
  `add_tenant_integrations.sql` and `add_whatsapp_device_mapping.sql` contain no
  `ENABLE ROW LEVEL SECURITY` and no `CREATE POLICY`. Whether the live tables
  have RLS is **unverified** — no database access.
- **P2-6 CONFIRMED — landing ships one 1,009 KB JS chunk** (302 KB gzipped), no
  code splitting. Typecheck and build both pass clean.

## What the full-history secret sweep actually found

Running gitleaks over all 170 commits reports **81 findings**. That number is
misleading on its own, so here is the breakdown, because three quarters of it
is not a leak:

| Category | Count | Verdict |
|---|---|---|

The lesson for the backlog item: point gitleaks at this repo and it will cry
wolf 81 times. The `.gitleaks.toml` committed here allowlists the placeholder

# The skeptic panel — and why the headline number is not what I planned

The design was: 14 specialist finders, then 3 independent skeptics per finding,
each prompted to refute, defaulting to refuted, majority rules.

**It did not complete.** The run hit the org spend limit: **399 of 428 agents
errored.** The first result set claimed "138 raw → 5 survived, 133 killed", and
that number is wrong in a specific and instructive way: a finding whose three
skeptics all failed on a quota error got zero votes, and my script scored zero
votes as "did not survive". Those 133 were **killed by billing, not by
skepticism**.

After the limit reset I resumed the run. Of the verdicts that actually
completed, the refutation rate is:

```
verdicts completed : 197
  refuted          :  16  (8%)
  not refuted      : 181
```

So the panel, when it ran, refuted about 8% of individual votes — nothing like
the 96% the first summary implied. **I am not reporting a kill count**, because
I do not have a trustworthy one. What I have instead is the CONFIRMED /
CONFIRMED (code) / REPORTED labelling above, where CONFIRMED means I ran the
command myself.

The panel did earn its keep once, decisively. The auth finding arrived as *"POST
/api/auth/change-password permanently poisons the shared client"* with a
reproduction. Two of three skeptics let it through. The third refuted it with
its own measurement showing that `update_user` fires `USER_UPDATED`, which
supabase-py maps back to the service key — so the change-password **success path
self-heals**, and only its error path leaks. It then pointed at
`sign_in_with_password`, which fires `SIGNED_IN` and is never restored.

I re-ran both paths myself:

```
login   before: Bearer SERVICE-ROLE-KEY-AAA
login   after : Bearer eyJhbGciOiAiSFMyNTYiL...     <- leaks, never restored
chgpw   before: Bearer SERVICE-ROLE-KEY-AAA
  after set_session : Bearer eyJhbGciOiAiSFMyNTYiL...
  after update_user : Bearer SERVICE-ROLE-KEY-AAA   <- self-heals
```

The majority was wrong, the lone refuter was right, and following its evidence
turned a wrong P0 into a real one at a different endpoint that fires on **every
login** rather than on a rare error path. That is the whole argument for
adversarial verification, and it is also the argument for not trusting a vote
count over a command you ran yourself.

Findings the finders produced, by claimed severity, for completeness:
**138 total — 15 P0, 42 P1, 48 P2, 33 P3; 99 claimed as reproduced.** Those
counts are the *finders'* self-assessment, not a verdict.

# What I could not verify

Stated plainly, because rounding these up to "working" would be the whole
failure mode this audit exists to catch.

- **The live database schema.** Supabase MCP returned *"You do not have
  permission to perform this action"* for project `lrwzlujomukzjykafmic`. All
  schema findings are code-vs-file only.
- **Phase 4 flows 2–6** — signup, login/logout/session expiry, the onboarding
  wizard, tenant isolation between two real tenants, and inbound-message →
  AI-reply → persisted. All of them need the core tables, and P0-6 means those
  tables exist in no migration. **No browser screenshots were taken**, because
  there was no working end-to-end flow to screenshot.

  Flow 1 (cold boot) **was** driven and is reported honestly: of 8 containers,
  6 reach healthy (`supabase-db`, `supabase-auth`, `supabase-gateway`,
  `landing`, `mailpit`, and `supabase-rest`, which runs healthcheck-less by
  necessity — the image is distroless). The `backend` container reaches
  `unhealthy`, correctly, because `/health/database` fails on the missing
  schema; and `bridge` never starts because it waits on a healthy backend.
  So: **the infrastructure boots, the application cannot.** That is the
  accurate statement, and the cause is P0-6.
- **Whether any of the unauthenticated endpoints (P0-3, P0-4) were actually
  abused.** That needs Supabase and Coolify access logs.
- **The torch-inclusive image size.** Only the stripped image was built.
- **Memory headroom for the worker/limit change** in the Dokploy compose. No
  load test was run; `WEB_CONCURRENCY=2` / `2G` is reasoned, not measured.
- **CORS between a Vercel-hosted landing and a Dokploy-hosted backend.** Flagged
  in the runbook, not checked.
- **The 137 findings I did not personally reproduce.** They are in
  `docs/HARDENING-BACKLOG.md` as leads.
