## 1. `e92ce16` — signal handlers no longer crash startup off the main thread

**Problem.** `BijouAI.__init__` called `signal.signal()` unconditionally.
CPython allows that only on the main thread, and `BijouAI` is constructed inside
FastAPI's startup event, so `with TestClient(app):` died on `__aenter__` with
`ValueError: signal only works in main thread of the main interpreter`. Every
in-process integration test was unrunnable.

**Change.** `_install_signal_handlers(instance)` installs when it can, skips with
a debug log when it cannot, and returns a bool so callers can distinguish. Off
the main thread the ASGI server owns SIGINT/SIGTERM anyway and the handler only
sets `running = False`, so nothing is lost. Added a module-level
`import threading` — the file previously reached threading only via
`__import__("threading")` at line 542.

A missing `_signal_handler` still raises `AttributeError` on purpose. That is a
call-site bug, not an environment difference, and swallowing it would hide it —
there is a test asserting it still raises.

**Test written first.** `tests/unit/test_signal_handler_thread_safety.py`, red
before the change:

```
E   ImportError: cannot import name '_install_signal_handlers' from 'src.core.bijou'
```

green after:

```
$ ./.venv/Scripts/python.exe -m pytest tests/unit/test_signal_handler_thread_safety.py -q -s
3 passed
```

**Verified at the layer that matters** — not just the unit test:

```
$ ./.venv/Scripts/python.exe -c "with TestClient(app) as c: ..."

```

The second test pins the other direction: handlers *are* still installed on the

## 2. `89b67f3` — login no longer overwrites the shared service-role credential

**Problem (P0).** `get_supabase()` is a process-wide singleton holding the
service-role key; every `.table()` call shares it, and RLS is service-role-only.
`auth_api` ran user-scoped auth on that same object, and supabase-py rewrites
`options.headers["Authorization"]` on `SIGNED_IN`/`TOKEN_REFRESHED`. Measured:

```
login   before: Bearer SERVICE-ROLE-KEY-AAA
login   after : Bearer eyJhbGciOiAiSFMyNTYiL...
BEFORE postgrest Authorization: Bearer SERVICE-ROLE-KEY-AAA
AFTER  postgrest Authorization: Bearer eyJhbGciOiAiSFMyNTYiL...
```

Nothing restored it, so every later request in that worker authorized as that
one user.

**Change.** `get_auth_client()` — a second singleton used only for auth. All five
session-mutating calls moved to it: `refresh_session`, `sign_up`,
`sign_in_with_password`, `sign_out`, `set_session`/`update_user`. Data access
keeps `get_supabase()`.

A second singleton rather than a per-request client, deliberately: the first
singleton exists because `create_client` per call opened a fresh httpx pool and
caused `ConnectionTerminated` under load, and there is a test pinning that the
auth client is reused.

### One of my own assertions was wrong and I corrected it

The first version of the isolation test asserted on
`data_client.postgrest.session.headers["Authorization"]`. That failed — and the
fix was not at fault. `get_supabase()` constructs the client with a custom
`httpx_client` to force HTTP/1.1, and in that configuration PostgREST's own
header dict is empty by construction:

```
with custom httpx_client -> postgrest hdr: None
with custom httpx_client -> options  hdr: 'Bearer SERVICE-KEY'
default client           -> postgrest hdr: 'Bearer SERVICE-KEY'
```

So the assertion would have passed vacuously against an empty dict in some
configurations and failed spuriously in this one. It now asserts on
`options.headers`, which is what supabase-py rebuilds the PostgREST client from,
with the measurement above recorded in the test as a comment. That is a **wrong
test corrected**, and it is called out here because the rule is that fixing a
test gets said out loud.

## 8. Bringing the local stack up actually found four more bugs

The compose file passed `docker compose config` and all three images built, and
it still did not work. Every one of these was found by running it, and each is
now fixed in `docker-compose.local.yml` (and, where it applies, in the Dokploy
one too).

**The init scripts never ran.** They were mounted as *directories* under
`/docker-entrypoint-initdb.d/`. The postgres entrypoint does not recurse:

```
/usr/local/bin/docker-entrypoint.sh: ignoring /docker-entrypoint-initdb.d/init-scripts
```

so GoTrue and PostgREST crash-looped on

```
FATAL: password authentication failed for user "supabase_auth_admin"
FATAL: password authentication failed for user "authenticator"
```

Now mounted as individual **files** with a `zz-` prefix so they run after the
`supabase/postgres` image's own `migrate.sh` — which, it turns out, already
creates the Supabase roles. So `00-roles.sql` now `ALTER`s their passwords
rather than `CREATE`-ing roles behind an `IF NOT EXISTS` guard that always
fired.

**Host ports were inside a Windows reserved range.**

```
Error response from daemon: ports are not available: exposing port TCP
0.0.0.0:54322: bind: An attempt was made to access a socket in a way
forbidden by its access permissions.
$ netsh int ipv4 show excludedportrange protocol=tcp
     54272       54371
```

Both `54321` and `54322` — the Supabase CLI convention — sit inside it. Now
`${LOCAL_SUPABASE_PORT:-9321}` and `${LOCAL_DB_PORT:-9432}`, overridable.

**`localhost` in healthchecks resolves to `::1` first.** `landing` sat
`unhealthy` with `wget: can't connect to remote host: Connection refused` while
nginx was serving perfectly on `0.0.0.0:3000` — because `Dockerfile.landing`
has `listen 3000;`, IPv4 only. All healthchecks now use `127.0.0.1`.

**PostgREST is distroless.** Its healthcheck could never run:

```
OCI runtime exec failed: exec: "/bin/sh": stat /bin/sh: no such file or directory
```

There is no shell and no `wget` in that image, so no `CMD`/`CMD-SHELL` probe is
possible. Its healthcheck is removed, the gateway depends on it with
`service_started`, and the gateway's own probe now goes through `/rest/v1/` —
which fails with a 502 if PostgREST is down. Same coverage, from a container
that has a shell.

## 16. `b15995e` — webhook backpressure (CVE-2026-003)

`/webhook/message` authenticated its caller and then bounded nothing. The only
middleware on the app is CORS and the no-cache pass, and the per-chat limiter in
`process_message` runs inside the background task — after the 200 has already
gone back. An authenticated flood was accepted at 100% and queued unbounded
work. `tests/security/test_call_security.py` had asserted this since February
and failed; the previous pass left it red on purpose, calling it a product gap.

Two token buckets. Global (60 burst, 5/sec) is the safety control — a
per-device limit alone is defeated by varying the device id, and the CVE test
does exactly that with 100 distinct ids. Per-device (120 burst, 20/sec) is
fairness. Over-limit is 429 + Retry-After, never a silent drop.

Two mistakes on the way, both caught by running the full suite rather than the
file:

- My first defaults (30/sec refill) passed the CVE test in isolation and failed
  it in the suite — 100 sequential requests refill faster than they arrive, so
  nothing was ever shed. A limiter tuned loose enough to be invisible is not a
  limiter.
- Module-global buckets bleed between tests: the flood emptied the bucket and
  429'd the next, unrelated test. Fixed by resetting in the autouse fixture, not
  by loosening the limit.

**A test asserted the vulnerability as a requirement.**
`test_maximum_call_tracking_capacity` demands ≥80% success across a 1000-request
flood — i.e. that the system must NOT shed load. That is irreconcilable with the
CVE test by construction. Resolved by scope, not by picking a winner: the load
tests measure the HANDLER, so six of them take an explicit `no_webhook_rate_limit`
fixture that says what they measure and why. `test_memory_exhaustion_protection`
deliberately does not, because backpressure IS its subject.

**One test fixed, stated plainly.** `test_memory_exhaustion_protection` was
unsatisfiable as written: its loop breaks on the first 429, so
`rate_limited_count` is always 1 when the branch runs, yet it asserted
`rate_limited_count > total_requests * 0.1` — literally `assert 1 > 6.3`. It
could not pass in any world. It now asserts what it can honestly observe (that
shedding engaged while load was still arriving); the shed proportion is asserted
in the new unit tests, against the bucket rather than wall-clock timing.
